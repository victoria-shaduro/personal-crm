# Design

## Context

Список контактов, поиск, группы, карточки и серверные операции сейчас работают с общей базой. В контактах уже есть ссылка на одну группу, заметки связаны с контактом. Первое обновление с входом требует переноса существующих записей. Мотивация описана в [предложении](proposal.md).

## Goals / Non-Goals

**Goals**

- Проверять доступ на сервере по текущему аккаунту при каждом чтении и изменении данных CRM.
- Перенести существующие записи с сохранением номеров, связей и содержимого. Проверить перенос на отдельной базе перед выкаткой.

**Non-Goals**

- Пароли, вход по коду или через соцсети, профиль и смена почты, удаление аккаунта, общий доступ, приглашения, роли и админка.

## Decisions

- **Вход и письмо.** Better Auth Magic Link использует PostgreSQL через Drizzle. Сервер обрабатывает запросы на один нормализованный адрес последовательно и хранит отпечаток активной ссылки и историю отправок для лимита. Успешная отправка заменяет предыдущую ссылку, повторное использование проверяется атомарно. Браузер передаёт одноразовый ключ в теле запроса. Маршруты входа доступны до проверки сессии, переходы после входа ведут внутри CRM.
- **Сессия и защита данных.** Отдельная сессия PostgreSQL на устройство. При посещении защищённой страницы продлеваются срок в базе и cookie браузера. Выход отзывает сессию этого устройства. Страницы, метаданные карточки и серверные операции получают идентификатор владельца из проверенной сессии. Запросы фильтруются по нему, включая оба запроса блока «Пора связаться». Проверка заметок идёт через контакт. Результаты с личными данными не попадают в общий кеш.
- **Схема записей.** У контакта и группы обязательный владелец. Уникальность нормализованного названия группы действует в пределах владельца. База проверяет, что назначенная контакту группа принадлежит тому же владельцу. Заметки сохраняют связь с контактом. Уведомления об ошибках чужого контакта совпадают с уведомлениями для отсутствующего.
- **SMTP.** Один транспорт Nodemailer получает настройки окружения. Локально и в CI используется только Mailpit, рядом с PostgreSQL. В проде используется тот же образ, Unisender Go по SMTP с TLS. Ключ Unisender Go и секрет Better Auth вводятся в окружении. Ссылки и секреты исключаются из журналов.

## Risks / Trade-offs

- Одновременные запросы могли бы обойти лимит или выдать две действующие ссылки. Последовательная обработка по адресу и одноразовая проверка в базе покрываются тестами на конкуренцию.
- Старое приложение может сохранить запись между копированием и переносом. При первом переходе его останавливают перед снятием копии.
- Сбой почтового сервиса не должен отменять предыдущую ссылку. Новое письмо подтверждается только после приёма через SMTP.

## Migration Plan

1. До merge показать владелице миграцию и результаты её прогона на отдельной базе с существующими контактами, заметками, группами и сроками. Сверить количества и связи. Владелица задаёт DNS и подтверждает отправителя в Unisender Go, затем заполняет параметры почты и входа на сервере.
2. На первой выкатке остановить старое приложение, снять резервную копию и связать её с SHA старого образа. Запустить миграцию разовым контейнером из нового образа. Одной транзакцией создать таблицы входа, подготовить аккаунт с почтой владелицы, назначить владельца существующим контактам и группам и закрепить ограничения базы. Ссылку на группу, заметки и даты не менять. Вход под почтой владелицы требует подтверждения письмом. Обе команды демо-данных используют тот же аккаунт.
3. После успешной миграции запустить новое приложение и проверить публичный `/health`. Сбой миграции останавливает запуск нового образа. При неудачном smoke сообщить владелице. Откат запускает она.
4. Для отката через границу входа использовать предвыкаточную копию вместе с соответствующим старым образом. Проверить пару, снять страховочную копию, дождаться подтверждения `yes` и восстановить базу через `restore.sh`. Старый образ запускать только после восстановления. Для обычного вызова `restore.sh` сохраняется правило запуска той же версии. Записи, сделанные после выбранной копии, остаются в страховочной копии текущей базы.

Миграция и обе команды демо-данных получают почту владелицы из переменной `OWNER_EMAIL` в `.env`. Владелица задаёт адрес самостоятельно.
