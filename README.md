# Личная CRM

Приложение для ведения личных контактов. Идея и главный сценарий — в `specs/01-продуктовая-идея.md`.

## Что нужно установить

- Node.js 24 (LTS)
- pnpm
- Docker Desktop — в нём работает база данных PostgreSQL

## База данных

База PostgreSQL 18 работает в Docker. Настройки описаны в `compose.yaml`, пароли — в файле `.env`.

### Первый запуск

1. Скопируйте `.env.example` в `.env` и заполните значения: имя пользователя, пароль, название базы и строку подключения `DATABASE_URL`. Файл `.env` не попадает в git.
2. Запустите Docker Desktop.
3. В папке проекта выполните:

   ```
   docker compose up -d
   ```

### Повседневная работа

- База запускается сама вместе с Docker Desktop. Отдельно включать её не нужно.
- Посмотреть, работает ли база: `docker compose ps`. В колонке STATUS должно быть `healthy`.
- Остановить базу: `docker compose stop`. Данные при этом сохраняются.
- Запустить снова: `docker compose up -d`.

Данные хранятся в томе Docker `personal-crm_postgres-data`. Команда `docker compose down -v` удалит его вместе со всеми контактами. Не используйте её, если не хотите стереть данные.

## Приложение

### Первый запуск

Когда база уже работает (см. выше), в папке проекта выполните по очереди:

1. `pnpm install` — установить зависимости.
2. `pnpm db:migrate` — создать таблицы в базе.
3. `pnpm db:seed` — по желанию: заполнить базу 1000 тестовых контактов с заметками. Работает только с пустой базой: если контакты уже есть, команда ничего не меняет.
4. `pnpm dev` — запустить приложение.
5. Откройте в браузере http://localhost:3000

### Повседневная работа

- Запустить: `pnpm dev` (Docker Desktop с базой должен быть запущен). Приложение откроется по адресу http://localhost:3000
- Остановить: в окне терминала, где запущено приложение, нажмите `Ctrl+C`. Данные при этом сохраняются — они в базе.
- Если вместо контактов видно «Не получилось загрузить данные» — запустите Docker Desktop и обновите страницу.

### Как проверить главный сценарий

1. Откройте http://localhost:3000 — виден список всех контактов и их число.
2. Нажмите «Добавить контакт», заполните имя и сохраните — вы вернётесь в список, новый контакт будет подсвечен.
3. Введите часть имени в поиск — список отфильтруется. Откройте карточку.
4. Напишите заметку и нажмите «Добавить заметку» — она появится в карточке с датой.
5. Откройте тот же адрес в другом браузере — там те же контакты и заметки.

### Как не терять связь

1. Откройте карточку контакта. В поле «Частота общения» выберите неделю, месяц, квартал или год и нажмите «Задать частоту». Если частота уже сохранена, кнопка называется «Изменить частоту». «Не задано» убирает расписание, сохраняя человека и его заметки; после сохранения кнопка снова называется «Задать частоту».
   При заданной частоте в информационном блоке карточки видна строка «Связаться» с запланированной датой по Новосибирску без времени. Если частота не задана, строки нет.
2. Каждый раз, когда вы сохраняете частоту, срок начинается заново от момента сохранения — даже при том же значении. Старые заметки не учитываются; сама настройка не создаёт заметку.
3. Новая заметка в карточке или галочка «Связались» на главной тоже начинают срок заново. Галочка добавляет заметку «Связались» с датой и временем. При отсутствии частоты заметки не создают расписание. Изменение имени, телефона и других данных срок не переносит.
4. На главной блок «Пора связаться» показывает всех просроченных первыми, затем до двух ближайших запланированных. Персиковый цвет означает просрочку. Поиск фильтрует только общий список ниже блока.
5. Нажатие на имя и дату открывает карточку. Галочка в блоке на главной отмечает общение без перехода; повторное нажатие во время запроса недоступно. При ошибке рядом появляется сообщение, можно повторить. В карточке общение записывается новой заметкой; черновик заметки остаётся при настройке частоты.

Периоды — ровно 7, 30, 90 и 365 суток по 24 часа. Дата в блоке показана без времени, всегда по Новосибирску. Просрочка определяется по точному моменту: сегодня после скрытого времени срока контакт уже просрочен. Статус пересчитывается при загрузке и переходах, без автоматического обновления по таймеру.

Проверка руками: сохраните частоту, обновите карточку и откройте её в другом браузере — значение должно совпасть. Добавьте заметку в карточке и вернитесь на главную — срок должен сдвинуться. Нажмите галочку в блоке на главной — срок должен сдвинуться снова. Уберите частоту — человек исчезнет из блока, а заметки останутся. При смене имени или телефона расписание сохраняется.

### Тестовые контакты для расписания

Только для локальной базы, после `pnpm db:migrate`:

```sh
pnpm exec tsx scripts/seed-keep-in-touch.ts
```

Скрипт добавляет семь отдельных контактов с обычными именами и пометкой о тестовых данных в описании: три просроченных, три будущих и один без расписания. Сроки заданы относительно времени запуска; у двух просроченных и двух будущих даты совпадают, чтобы проверить устойчивый порядок. Один контакт имеет длинное имя для проверки телефона. Скрипт не меняет существующие контакты и не включён в выкатку или обычный seed; каждый повторный запуск добавляет новую семёрку.

Если других расписаний нет, сразу после запуска видны пять записей: Ольга Лебедева, Михаил Соколов, Мария Кузнецова, Анна Смирнова и Александра Константиновна Рождественская. Елена Морозова пока скрыта, Алексей Петров не попадает в блок, поскольку частота не задана. Другие контакты с расписанием тоже участвуют в общем порядке.

Эти пять записей нужно смотреть в отдельном блоке «Пора связаться» над поиском: там показаны имя, дата и галочка. Общий алфавитный список ниже поиска содержит всех людей, включая контакты без расписания. После заметок, галочек и сохранения частот демонстрационные даты и состав верхнего блока меняются; исходный пример относится к только что добавленной семёрке.

Проверка блока:

1. Введите в поиск имя, которого нет, — блок сохранит состав и порядок. Откройте его ссылку клавишей Enter, вернитесь назад и обновите страницу.
2. Отметьте просроченного галочкой на главной и ручной заметкой в карточке: просрочка исчезает, а человек остаётся среди будущих только при попадании в два ближайших.
3. Меняйте частоты и убирайте расписания у тестовых контактов: проверьте только будущих (максимум два), одного будущего, только просроченных и отсутствие всех расписаний («Пока нет запланированных контактов»).
4. На телефоне проверьте перенос длинного имени и отдельную галочку; при другом часовом поясе устройства дата должна совпасть. На клавиатуре проверьте выбор частоты, сохранение, ссылки и галочки.
5. Удаление тестового контакта проверяйте отдельно и осознанно: удаление необратимо. После удаления ближайшего контакта его место занимает следующий подходящий. Для проверки агентом нужно отдельное согласие владельца.

### Команды

| Команда | Что делает |
| --- | --- |
| `pnpm dev` | запускает приложение для работы и разработки |
| `pnpm db:migrate` | применяет к базе новые изменения структуры таблиц |
| `pnpm db:generate` | создаёт файл миграции после изменения схемы в `src/db/schema.ts` |
| `pnpm db:seed` | заполняет пустую базу тестовыми контактами |
| `pnpm build` | собирает приложение и проверяет код на ошибки |
| `pnpm lint`, `pnpm typecheck` | проверки кода |

## Работа над фичами через OpenSpec

В проект подключён [OpenSpec](https://openspec.dev/docs/setup) для Codex. Документы пишем на русском; служебные заголовки OpenSpec и ключевые слова SHALL/MUST остаются на английском, чтобы работали проверки.

OpenSpec установлен отдельно от приложения официальным установщиком. На новом компьютере для macOS или Linux выполните:

```sh
curl -fsSL https://openspec.dev/cli/install.sh | sh
openspec --version
```

Настройки проекта — в `openspec/config.yaml`, навыки Codex — в `.agents/skills/`. Они хранятся в git; после клонирования повторно запускать `openspec init` не нужно.

Порядок работы в Codex:

1. Выберите навык `openspec-explore`, чтобы обсудить идею и уточнить требования.
2. Выберите `openspec-propose` и опишите фичу: появятся предложение, требования и задачи в `openspec/changes/<имя-фичи>/`, а при необходимости — технический план.
3. Проверьте документы. Затем отдельно попросите применить изменение через `openspec-apply-change`.
4. После выполнения задач и проверки критериев приёмки используйте `openspec-archive-change`: требования попадут в `openspec/specs/`, а завершённое изменение — в `openspec/changes/archive/`.

В настольном Codex навыки доступны в боковой панели Skills. В Codex CLI и расширении для редактора их можно вызвать по имени, например: `$openspec-propose keep-in-touch: <описание фичи>`. Если новые навыки не появились, перезапустите Codex.

Проверка подключения из папки проекта:

```sh
openspec --version
openspec list --specs
openspec validate --all --strict --no-interactive
```

Ожидается: установленная версия, спека `delete-contact` в списке и успешная проверка. Для обновления CLI используйте `openspec install`, затем `openspec update` в проекте для обновления навыков Codex.

## Автовыкатка на сервер

Приложение: https://app.завяжи-узелок.рф. Сервер: `78.24.223.28`, пользователь `crmapp`, папка `/home/crmapp/personal-crm`.

После каждого push в `main` GitHub Actions автоматически:

1. Проверяет код и собирает Docker-образ с полным SHA коммита в качестве тега.
2. Отправляет образ в GHCR и копирует скрипты из `deploy/` на сервер.
3. Поднимает отдельную PostgreSQL в Docker, в проекте Compose `prod`.
4. Применяет миграции разовым контейнером из нового образа. Если они завершились с ошибкой, новая версия приложения не запускается.
5. Запускает приложение, затем проверяет публичный `/health`: ответ должен быть `200`, база и таблицы доступны, номер версии совпадает с коммитом.
6. После успешной проверки оставляет на сервере текущий и предыдущий образы приложения. Логи каждого контейнера ограничены тремя файлами по 10 МБ.

База доступна только внутри Docker. Приложение слушает `127.0.0.1:3000`, nginx принимает HTTPS. База сервера и база на компьютере независимы. Данные сервера хранятся в томе `prod_postgres-data` и сохраняются между выкатками. Не выполняйте `docker compose down -v`: это удалит данные.

Чтобы выкатить новую версию, сохраните изменения в git и отправьте их в `main`. Если изменили схему базы, сначала выполните локально `pnpm db:generate` и добавьте полученные файлы `drizzle/` в тот же коммит. Статус виден во вкладке [Actions → Deploy production](https://github.com/victoria-shaduro/personal-crm/actions/workflows/deploy.yml). В конце зелёного прогона будет SHA выкаченной версии и успешная проверка `/health`.

Проверка руками:

```sh
curl -fsS https://app.xn----7sbgnddegvj7a8c6i.xn--p1ai/health
```

Ожидается `{"status":"ok","revision":"<SHA коммита>"}`. Также откройте приложение: должны работать список контактов, поиск и карточки.

### Первичная настройка

Настройки репозитория GitHub:

- Secrets: `DEPLOY_SSH_KEY` (отдельный закрытый ключ деплоя), `DEPLOY_KNOWN_HOSTS` (проверенный SSH-ключ сервера).
- Variables: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_DIR`, `PUBLIC_HEALTH_URL`.
- Образы публикуются с временным `GITHUB_TOKEN`. Этот токен используется сервером только для скачивания образа; временный файл авторизации удаляется после прогона.

На сервере владелец сам создаёт `/home/crmapp/personal-crm/.env` с правами `600`. Нужны `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` и `DATABASE_URL`. Формат строки подключения: `postgresql://<пользователь>:<пароль>@db:5432/<база>`. Для пароля удобно использовать результат `openssl rand -hex 24`: его не нужно дополнительно кодировать для URL. Эти значения должны совпадать во всех четырёх строках. У существующей базы изменение пароля в `.env` само по себе не меняет пароль PostgreSQL.

Для переключения подготовленной заглушки nginx на приложение владелец один раз выполняет на сервере:

```sh
sudo bash /home/crmapp/personal-crm/deploy/setup-server.sh
```

Скрипт сохраняет резервную копию и меняет только конфигурацию приложения `crm-app.conf`. Настройки лендинга и сертификаты сохраняются.

### Ошибка и ручной откат

Красный прогон означает неудачную выкатку. Автоматического отката нет. Ошибки миграций останавливают запуск новой версии; ошибка проверки `/health` также завершает прогон с ошибкой. Причина видна в журнале Actions.

Чтобы вручную вернуть последнюю успешную версию после сбоя или предыдущую версию после успешной выкатки:

```sh
ssh crm 'cd /home/crmapp/personal-crm && bash deploy/rollback.sh'
```

Откат меняет только образ приложения и снова проверяет `/health`. Данные и миграции назад не откатываются, поэтому изменения схемы должны быть совместимы с предыдущей версией приложения. Также можно явно указать сохранённый образ: `bash deploy/rollback.sh ghcr.io/victoria-shaduro/personal-crm:<полный SHA>`.

### Тестовые данные

После первой успешной выкатки база один раз заполняется командой:

```sh
ssh crm 'cd /home/crmapp/personal-crm && bash deploy/seed-once.sh'
```

Она добавляет 1000 тестовых контактов с заметками только в пустую базу. Файл `.seed-complete` предотвращает повторный запуск; последующие выкатки тестовые данные не добавляют. Если контакты уже есть, заполнение пропускается.

### Как проверить удаление контакта

1. Откройте карточку контакта с заметками.
2. Рядом с «Изменить» нажмите «Удалить контакт» (на телефоне — значок корзины): окно показывает имя и предупреждение.
3. Нажмите «Отмена» или Escape — контакт, заметки и несохранённый текст новой заметки остаются.
4. Повторно откройте окно и нажмите «Удалить» — откроется список с сообщением «Контакт удалён», число контактов уменьшится.
5. Найдите контакт по имени: его больше нет. Старые адреса карточки и редактирования показывают «Контакт не найден».
